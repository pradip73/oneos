# The OneOS repository

OneOS's own programs — the desktop shell, the helpers, the policy — are built into a
package, `oneos-desktop`, and served from a signed apt repository on GitHub Pages:

    https://pradip73.github.io/oneos/apt

A machine installed from the ISO trusts this repository from its first boot and
receives new versions of OneOS through the ordinary **Updates** screen. Debian
itself still comes from Debian; this repository carries only what is ours.

Everything is in place except the signing key, which cannot be generated by the
build for the same reason a bank cannot choose your PIN. It is generated once, by
you, and never leaves your hands except as a GitHub secret.

## One-time setup — about ten minutes

You need a terminal on any Linux machine. **The OneOS VM is fine**: open
Terminal from the Start menu.

### 1. Generate the key

```bash
gpg --batch --quick-generate-key "OneOS Archive <oneos@localhost>" ed25519 sign 5y
```

That makes an Ed25519 signing key valid for five years. Then find its fingerprint:

```bash
gpg --list-secret-keys --with-colons | awk -F: '/^fpr/ {print $10; exit}'
```

Copy that 40-character string; call it `FPR` below.

### 2. The public half goes into the repository

```bash
gpg --armor --export FPR > oneos-archive.asc
```

Put that file at `packaging/oneos-archive.asc` in the git repository and commit it.
It is public by nature — it is what every OneOS machine uses to *check*
signatures, and it cannot make them.

### 3. The private half goes into a GitHub secret

```bash
gpg --armor --export-secret-keys FPR
```

Copy the whole output, from `-----BEGIN PGP PRIVATE KEY BLOCK-----` to the END
line. Then, on GitHub: **Settings → Secrets and variables → Actions → New
repository secret**, name `APT_SIGNING_KEY`, paste, save.

**Keep a copy somewhere offline as well.** If this key is lost, every installed
OneOS machine stops trusting updates and needs the keyring reinstalled by hand.

### 4. Turn on GitHub Pages

**Settings → Pages → Build and deployment → Source: Deploy from a branch →
Branch: `gh-pages`, folder `/ (root)`.** The branch will not exist until the first
publish, so do this step after step 5 if GitHub will not let you pick it yet.

### 5. Publish

Push the commit from step 2, or run **Actions → Publish OneOS repository → Run
workflow**. It builds the packages, signs the index with your key, verifies that the
committed public key really is the other half of the secret, and pushes the
result to `gh-pages`.

The next ISO build after that includes the keyring package, and every machine
installed from it is on the repository from its first boot.

## What the workflow refuses to do

- **Publish unsigned.** With no secret it stops with an error. An unsigned
  repository would teach apt to trust whatever appears at a URL.
- **Publish with mismatched keys.** If `packaging/oneos-archive.asc` is not the
  public half of `APT_SIGNING_KEY`, it stops, because the ISO would then trust one
  key while the repository signs with another and every update would fail with
  an error the user cannot act on.
- **Delete old versions.** Previously published packages stay in the pool, so a
  machine mid-way through an upgrade never finds its files gone.

## How a version becomes an update

Every publish is versioned `VERSION+YYYYMMDD.commit` — for example
`0.2.0+20260918.e0ea7f6`. Each is newer than the last in apt's ordering, so a
push to `main` that changes anything under `build/config/includes.chroot/`
becomes an update on every installed machine at its next check.

To make a release, change `VERSION`. Everything published afterwards sorts above
everything published before.

## Where this sits in the plan

`docs/ARCHITECTURE.md` §6.2 describes `aptly` with dev/beta/stable channels and a
mirrored Debian. This is the first, static version of that: one channel, one
architecture, served as files. It is enough to update OneOS's own packages, which
is the thing that was missing. Channels and promotion come when there is a second
audience to promote to.
